## Bug B1 — Consent withdrawal is promised by the notice but no shipped path can exercise it

- Suggested tier and practical impact: **Big bug (3)**. The consent notice — the product's own trust contract, rendered to every participant — states "You may withdraw AI or recording permission separately. Withdrawal pauses the review." (served by `consent.py`, rendered by `ConsentForm.tsx`). No shipped client can exercise that right: the only consent writer in the frontend hard-codes both permissions to `true` and is unreachable after consent is granted, and no other UI affordance exists. A participant who wishes to withdraw has only *Pause/Finish*, which the notice itself distinguishes from withdrawal. Because recording is room-level (LiveKit Egress records the room, not a participant's tracks), closing the tab does not withdraw anything: the recorder keeps running until a server-side fence. This is a material failure of a consent boundary, not a cosmetic gap.
- Contribution group and any related entries: **B1** — single root cause (the withdrawal flow was never completed end-to-end), with two symptoms kept together deliberately: (a) the missing UI affordance, and (b) the backend's complete-but-unreachable withdrawal receipt machinery (receipt bindings and a DB constraint that no shipped client can ever trigger). Per the dedup rule these are one finding, not two.
- Evidence status: **source-supported-not-run** (complete static trace; execution is unnecessary for (a) because the claim is the *absence* of any path, and impossible for (b)'s end-to-end reach without a database, which is outside the pack's offline boundary).
- Affected file(s) and line(s), or exact UI path:
  - Promise: `submission/src/beep_agent/consent.py` lines 33–47 — `notice` construction; line 45 is the `withdrawal` string quoted above. Rendered verbatim by `submission/web/src/ConsentForm.tsx` line 153 (`<p className="fine-print">{notice?.withdrawal}</p>`).
  - Missing affordance: `submission/web/src/ConsentForm.tsx` lines 91–104 — the form's only submit path sends `{ai: true, recording: true, ...}` (checkboxes `ai`/`recording` start `false` and the submit button is `disabled={!ai || !recording || disabled}`, line 175); `submission/web/src/types.ts` lines 27–30 — `ConsentDecision` types both flags as the literal `true`, making a reduced decision unrepresentable; `submission/web/src/Review.tsx` line 1095 — the form is mounted only when `isParticipant && !hasConsent(ownConsent) && !terminal`, so once consented the participant can never reach it again; exhaustive scan of `web/src` (verified by search) shows no other call to `mutate("consent", …)` or any control that sends `false`.
  - Backend symptom: `submission/src/beep_agent/store.py` `_consent_receipt_context` (lines ~396–412) — the `reducing_only` branch writes `notice_binding="withdrawal_prior_notice"` with the *prior receipt's* stored `policy`, or `"withdrawal_notice_unavailable"`; the branch is fully implemented yet unreachable from any shipped client (the missing-affordance bullet above), so its withdrawal receipt bindings and the DB CHECK that anticipates them (`policy IS NOT NULL OR notice_binding='withdrawal_notice_unavailable'`) are dormant machinery — which, together with the code's own comment ("Withdrawal remains possible, with the historical gap explicit"), is evidence the flow was designed but never wired up end-to-end.
  - Server-side persistence of the problem: `submission/src/beep_agent/recording.py` (Egress writes to the room bucket; no participant-scoped stop) and `realtime.py` `room_entrypoint` — nothing stops recording when a participant disconnects (`close_on_disconnect=False`; `RecordingService.stop` is only invoked from worker `recording_stop` jobs, which are enqueued only by fences in `store._fence`).
- Requirement or expected behaviour: By the notice's own text (a supported requirement served to participants): a consented participant must be able to withdraw AI permission or recording permission separately, and withdrawal must pause the review.
- Reachable preconditions and minimal fictional input: Any session where the participant has consented (the normal state of every active review). The participant then looks for a way to withdraw — the exact action the notice just promised them.
- Reproduction steps or complete source trace: See `evidence/B1-withdrawal-not-implemented.md`. Short form: (1) consent as a client or facilitator using the shipped UI — both flags forced true by the form; (2) observe the notice's withdrawal sentence rendered above the consent history; (3) search the consented participant's UI for any withdrawal control — none exists (form unmounts on consent; dock offers only Pause/Finish/Resume/Handover/Takeover); (4) close the tab instead — server-side session stays `active`, `recording_status` stays `recording`, the egress keeps writing (no fence fires on disconnect); (5) for the backend symptom: trace `set_consent` with a reduced decision → `_consent_receipt_context` → `withdrawal_prior_notice` → the stored `policy` blob → `consent_policy(settings).notice` — no `withdrawal` key has ever existed in any served notice, so the receipt's claimed prior notice could never have been rendered to the participant.
- Expected result: A consented participant can withdraw either permission separately from the review UI; the server records the withdrawal receipt and pauses the review.
- Actual result (source-verified prediction): No withdrawal path exists in any shipped client; the only state-changing options are Pause/Finish (local capture stop, not consent withdrawal). If a withdrawal is performed via the raw API (the endpoint `POST /api/sessions/{id}/consent` accepts `false`), the backend handles it correctly (fence, pause, receipt) — the machinery works, but only via raw HTTP, never via the product. Closing the tab stops local capture only; server recording continues until someone with control pauses or the time/budget fence fires.
- Relevant evidence file/excerpt under `evidence/`: `evidence/B1-withdrawal-not-implemented.md` (full line-referenced trace, including the exhaustive search commands proving no withdrawal affordance exists in `web/src`).
- Who/what is affected and under which conditions: Every participant in every active review who wishes to exercise the advertised right; the operator's compliance story (receipts that would misdescribe what was shown); the client whose voice/screen keep being recorded server-side after they leave, contrary to their intent to withdraw.
- Likely root cause and uncertainty: The withdrawal flow was designed (notice text, DB constraint, receipt bindings, epoch-fencing in `_fence`/`set_consent` all anticipate it) but never completed: the frontend affordance was never built, the consent type forbids `false`, and the notice itself lacks the `withdrawal` field its receipt path presumes. Uncertainty: none about the code shape; the only judgement call is tier (consent-boundary material failure → big bug per `SCORING.md`), which is the assessor's to confirm.
- Proposed fix: Either complete the flow or stop promising it. Minimal honest fix: add per-permission withdrawal controls to the consented participant view that POST the current decision with one flag set to false (the backend already fully supports this: `set_consent` handles reduction, fences, pauses, and receipts). Optionally harden the receipt record by binding withdrawal receipts to the *current* policy with a withdrawal-specific binding; no notice-version bump is required, since the notice already advertises withdrawal.
- Regression check: Before the fix, no UI sequence reduces a consent flag, and an API-level withdrawal yields a receipt whose stored `policy["notice"]` has no `withdrawal` key; after the fix, a UI test drives withdrawal from the consented view, the session pauses with a bumped `consent_epoch`, and a receipt with a withdrawal notice binding is written — meaning the existing withdrawal cases in `tests/test_consent_receipts.py` finally exercise a path the shipped UI can actually reach.

## Improvement I1 — Expose transient recording/job failures in session state instead of silent self-healing

- Suggested tier and why the contribution meets it: **Decent improvement (10)** — specific, grounded in this snapshot, feasible with a bounded change, with measurable acceptance checks.
- Contribution group and any overlap with a reported bug/improvement: **I1**. Distinct from B1 (consent withdrawal flow); a different subsystem and mechanism.
- Evidence of the need in this snapshot: `worker.py` `_recording` wraps `set_recording(..., "failed", eid)` in `with suppress(StoreError)` on both the start-failure and stop-failure paths, discarding the `RecordingError` reason; `store.observe_recording` silently flips a failed health check into `recording_status="failed"` + pause with no reason recorded; `Operator.tsx` renders only `statusLabel(...)` and `session.recording_status`, so an operator sees "failed" with no explanation and must query `beep_jobs` directly to learn why.
- Who benefits and what changes for them: operators diagnosing "Review interrupted"/"Paused" sessions; facilitators explaining a paused review; on-call engineers who otherwise need database access.
- Proposed change, affected components and implementation approach: when `set_recording(status="failed")` or `observe_recording` fires, record a bounded `last_recording_failure` on the session document: `{reason: <fixed label already used by RecordingError>, egress_id, reservation_id, at}` (fixed labels only, one slot, overwritten). Render it in the operator's session ledger and review header, operators only.
- Why this is distinct from other entries, or which lower-tier claim it replaces: distinct need (observability, not consent or lifecycle semantics); distinct mechanism (a bounded session field + operator-only rendering).
- Measurable acceptance criteria and realistic checks: (1) any `set_recording(status="failed")` results in `GET /api/sessions/{id}` containing `last_recording_failure.reason` from the fixed label set, with a timestamp; (2) the operator session list shows a failure indicator within one poll interval; (3) non-operator API responses do not contain the field; (4) a `tests/test_api.py` case covers all three.
- Relative effort and assumptions: small (~1–2 h); no new dependency; follows the existing fixed-label discipline of `RecordingError`.
- Dependencies, risks and trade-offs: slight session-document growth (bounded to one entry); must not leak exception text (reuse fixed labels only).
- Why this is worth doing rather than an alternative: log-only alternatives still require host access; doing nothing leaves every transient failure — including ones that look like lifecycle wedges — a silent partial report. This is the smallest change that makes recording failures diagnosable from the existing operator UI.
- Optional implementation: not implemented (review-only submission); acceptance criteria remain untested.

## Improvement I2 — Consent-notice versioning and participant-visible receipts

- Suggested tier and why the contribution meets it: **Decent improvement (10)** — completes the consent-provenance story the backend already implements but never surfaces to the person it protects.
- Contribution group and any overlap with a reported bug/improvement: **I2**. Distinct from B1: B1 is the missing withdrawal flow; I2 is participant-facing notice versioning and receipt publication (forward-looking provenance, independent of whether withdrawal exists).
- Evidence of the need in this snapshot: `consent.py` stamps `notice_version` and `policy_id = content_hash(policy)`, but `ConsentForm.tsx` never displays which version a participant accepted, and the existing endpoint `GET /api/sessions/{id}/consent-receipts` (`api.py`, backed by `store.list_consent_receipts`) has **no frontend consumer** (verified: no non-test component references it).
- Who benefits and what changes for them: participants (can see and later recall exactly what they agreed to); facilitators answering "what did I sign?"; compliance reviewers (version traceability without DB access).
- Proposed change, affected components and implementation approach: (1) render `notice_version`/`policy_id` from the server's consent response in `ConsentForm` after acceptance; (2) add a "My consent receipts" section to the participant's `ReportView` consuming the existing endpoint (already role-scoped server-side), showing `seq`, `role`, flags, `notice_binding`, `policy_id` — not the full policy blob.
- Why this is distinct from other entries, or which lower-tier claim it replaces: distinct need (provenance visibility vs. flow completion); distinct mechanism (frontend consumption of an existing endpoint).
- Measurable acceptance criteria and realistic checks: (1) after consent, the participant sees the exact `notice_version`/`policy_id` accepted, sourced from the server response; (2) the receipts list shows the participant's own receipts with role, flags and binding; (3) a facilitator cannot see the client's receipts (server scoping; covered by a `tests/test_api.py` assertion); (4) a `ConsentForm.test.tsx` case asserts the version render.
- Relative effort and assumptions: small (~2–3 h); assumes the existing endpoint payload is sufficient, which it is (`list_consent_receipts` returns all fields needed).
- Dependencies, risks and trade-offs: none new; small UI surface growth; avoid dumping full policy JSON.
- Why this is worth doing rather than an alternative: the backend already does the hard, correct part (immutable, epoch-bound, hash-bound receipts); surfacing them converts an internal audit trail into a consent artifact the participant can actually check.
- Optional implementation: not implemented; acceptance criteria remain untested.

## Improvement I3 — Session preflight for room-token admission

- Suggested tier and why the contribution meets it: **Decent improvement (10)** — converts a class of opaque join failures into self-explanatory UI using logic the backend already computes.
- Contribution group and any overlap with a reported bug/improvement: **I3**. Distinct from I1 (post-hoc failure visibility vs. pre-join clarity) and from B1.
- Evidence of the need in this snapshot: `Review.tsx` `join()` only validates identity/room/URL *after* receiving a token; when `POST /room-token` fails (recorder not fresh, facilitator missing, session changed), `_room_admission`'s specific preconditions (`_require_room_admission`: status, both consents, recording freshness) collapse into a bare 409/503, which the UI maps to a generic "The media room could not connect." The backend already computes every prerequisite; it just returns none of them on failure.
- Who benefits and what changes for them: participants (actionable pre-join guidance instead of a generic error); operators (fewer escalations); the room (fewer half-joined states to reconcile).
- Proposed change, affected components and implementation approach: add `GET /api/sessions/{id}/admission` returning `{eligible, reasons: <fixed labels>}` derived from the same `_require_room_admission` checks the token endpoint performs; gate the join button on it and render `reasons` in the "Your next step" panel.
- Why this is distinct from other entries, or which lower-tier claim it replaces: distinct need and mechanism (read-only diagnostic endpoint + UI gating; no state mutation, no fencing risk).
- Measurable acceptance criteria and realistic checks: (1) with a recorder not yet fresh, the endpoint returns `eligible:false` with a fixed reason label; (2) the join button is disabled and shows that reason; (3) when all prerequisites pass, join flow is unchanged; (4) `tests/test_api.py` covers the not-fresh case.
- Relative effort and assumptions: small (~2–3 h); reuses the factored-out `_require_room_admission`.
- Dependencies, risks and trade-offs: one extra poll per participant; fixed label set only (no internal detail leakage).
- Why this is worth doing rather than an alternative: the checks already exist and run on every token request; surfacing them is nearly free and complements I1 (operator-side) without overlapping it.
- Optional implementation: not implemented; acceptance criteria remain untested.
